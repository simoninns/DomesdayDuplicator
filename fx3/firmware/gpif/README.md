# GPIF II state machine

The GPIF II block is the FX3's programmable parallel interface — it is what actually clocks
data in from the FPGA. Its behaviour is defined by a state machine designed in Cypress'
**GPIF II Designer**, not written by hand.

## What is in here

| Path | Contents |
| --- | --- |
| `DomesdayDuplicator.cydsn/DomesdayDuplicator.cyfx` | The GPIF II Designer project — the editable source |
| `DomesdayDuplicator.cydsn/projectfiles/` | Designer's model, view and timing-simulation XML |
| `IO_Matrix_view.PNG` | Screenshot of the I/O matrix configuration |
| `State_Machine_view.PNG` | Screenshot of the state machine |

## The build does not use any of it

The build consumes **`../src/domesday-duplicator-gpif.h`**, which is the Designer's generated
C output and is committed to the repository. Nothing in `CMakeLists.txt` reads the `.cyfx`
project, and no build step regenerates the header.

That is deliberate. GPIF II Designer is a Windows-only closed-source GUI tool with no
command-line interface, so it cannot participate in a reproducible build. Committing its
output keeps the firmware buildable on any platform.

The committed header records the revision that produced it in its own banner:

```
 * Project Name: DomesdayDuplicator.cyfx
 * Time : 08/15/2018 15:11:41
 * Device Type: FX3
 * Project Type: GPIF2
 * This file is generated by Gpif2 designer tool version - 1.0.1198.2
```

so the header currently in the tree came from **GPIF II Designer 1.0.1198.2** on
**2018-08-15**.

## Changing the state machine

This is a manual, Windows-only step:

1. Open `DomesdayDuplicator.cydsn/DomesdayDuplicator.cyfx` in GPIF II Designer (part of the
   Cypress/Infineon EZ-USB FX3 SDK; it also runs under Wine).
2. Edit the state machine or the I/O matrix.
3. Build the project. Designer writes a `cyfxgpif2config.h`-style header.
4. Copy that output over `../src/domesday-duplicator-gpif.h`.
5. Refresh `IO_Matrix_view.PNG` and `State_Machine_view.PNG` if the diagrams changed.
6. Commit the `.cyfx` project, the regenerated header and the screenshots **together** — the
   header is the only part the build sees, so a project change without a regenerated header
   is invisible, and a header change without the project is unreproducible.
7. Note the Designer version in the commit message if it differs from the one above.

Because it cannot be automated, this step is expected perhaps a handful of times per decade.
The header should be treated as source: reviewed on change, never edited by hand.
